# Qwen3-8B 三组训练的计算优化与缓存审计

- 审计日期：2026-09-10
- 对象：Trace+FoldGRPO、no-Trace、Trace-only 三组 Qwen3-8B BrowseComp 训练
- 目标：确认当前训练链路是否使用 KV cache、prefix cache 命中复用、批处理、并行计算及其它显存/吞吐优化
- 结论等级：以源码、实际启动参数和训练日志为准；“开关已打开”不等于“命中率或吞吐收益已被测量”

## 1. 结论摘要

当前链路已经做了多层计算优化，但训练和 rollout 必须分开看：

1. **Rollout 推理启用了 KV cache 和 prefix caching。** 三组实际运行日志都出现 enable_prefix_caching=True；vLLM 以 V1 引擎、chunked prefill 和批量调度运行。
2. **存在为 prefix cache 服务的 sticky-session 路由。** 多轮请求先固定到同一个 rollout server，使相同前缀有机会在同一 vLLM 实例中复用。
3. **没有可审计的 cache-hit 数值。** 三组训练 JSONL 中没有 cache-hit/cached-token 字段；实际运行还设置了 disable_log_stats=True，因此不能从当前产物给出命中率、缓存节省 token 或加速比。
4. **训练 actor 的 log-prob/PPO 前向显式关闭 KV cache。** actor 代码使用 use_cache=False。这是训练路径的设置，不应与 rollout 推理缓存混为一谈。
5. **rollout 请求存在并发。** 一个 batch 中的样本通过 asyncio.create_task + asyncio.gather 并发提交；vLLM 再以 max_num_seqs=8、max_num_batched_tokens=16384 做调度。agent loop worker 数为 1 会限制 Ray worker 层扩展，但不关闭 batch 内异步并发。
6. **训练侧启用了 bf16、FSDP 参数/优化器 offload、Ulysses sequence parallel、remove padding 和 gradient checkpointing。** actor 的 use_torch_compile=False；rollout vLLM 从实际日志看启用了 Inductor/CUDA Graph 编译路径。
7. **两组 Trace 还有一条额外的 frozen-reference 计算路径。** 它在独立 GPU 上以 bf16、inference mode 对每个决策前缀做串行评分，并显式 use_cache=False；no-Trace 不承担这部分开销，因此三组计算预算并不完全相同。

## 3. KV cache 与 prefix cache

### 3.1 Rollout 的 KV cache：已使用

rollout 配置类的默认值包括：

- free_cache_engine=True：允许在训练/rollout 模式切换时释放和恢复推理引擎内存
- enable_prefix_caching=True
- enable_chunked_prefill=True
- vLLM rollout dtype 为 bfloat16

vLLM 参数构造函数把这些配置直接传给引擎。vllm_async_server.py:263-267 传入最大上下文、序列数、chunked prefill、batch token 上限和 prefix caching；enable_prefix_caching 不是只存在于配置对象，而是进入了实际 vLLM 启动参数。

三组实际日志进一步确认 effective config：

- enable_prefix_caching=True
- chunked_prefill_enabled=True
- max_seq_len=40960
- tensor_parallel_size=2
- vLLM V1 compilation config 中 use_inductor=true、use_cudagraph=true

因此可以确认：rollout 解码期间由 vLLM 管理的 KV cache 在运行。这里说的是推理引擎内部的 KV block/cache，不是训练 actor 的 use_cache 参数。

### 3.2 Prefix cache 命中：机制存在，命中率未知

AsyncLLMServerManager 的类注释和实现包含两层机制：

- least-requests load balancing
- sticky session：多轮请求发送到同一 server，以支持 automatic prefix caching

代码把 request_id 映射到 server 的 LRU cache，最大 10000；后续同一 request ID 会选回同一实例。agent loop 的一次多轮会话因此不会在 server 之间随机漂移，vLLM 再根据 token 前缀判断能否复用 cache。

边界如下：

1. 路由保证的是让命中成为可能，不是每次都命中。不同 trajectory 的 prompt、tool observation、branch/fold 内容经常不同，任何 token 差异都可能截断可复用前缀。
2. AsyncLLMServerManager.generate 调用底层 server 时为每一轮生成新的底层 request ID，但 server 选择使用的是外层会话 request ID。因此 sticky session 保证实例粘性，真正的 prefix 复用仍由 vLLM 对 token 前缀做匹配。

### 3.3 缓存生命周期：会被训练模式切换打断

当前是 hybrid engine。free_cache_engine=True 时：

1. rollout 开始前恢复 weights；
2. 权重同步完成后恢复 kv_cache；
3. trainer mode 会 release rollout engine；
4. vLLM server 的 sleep 路径会先调用 reset_prefix_cache()，再 sleep；
5. clear_kv_cache() 也直接调用 reset_prefix_cache()。

所以 prefix cache 主要在同一轮 active rollout 的多轮请求之间有复用机会。跨训练 step 或训练/rollout 模式切换的持久复用不能假定存在；每次 reset 后，之前积累的 prefix blocks 不再可命中。

## 4. 缓存命中当前能否量化

结论：**不能从现有实验产物量化。**

已检查三组训练目录的 metrics/rollout JSONL，未发现以下字段或同义统计：

- cache hit / cache hit rate
- prefix cache hit
- cached tokens / prompt tokens cached
- KV cache usage / cache savings

同时，三组运行日志的 rollout 配置均为 disable_log_stats=True。日志里能看到 prefix cache 开关和引擎初始化信息，但没有稳定的 cache-hit 计数。现有分析报告中的“重复 search”“相同工具调用”也不是 KV/prefix cache 命中，不能互相替代。

因此本次报告不把 enable_prefix_caching=True 写成“已获得 X% 加速”。要得到可比较数据，下一轮至少应：

1. 将 rollout 的 disable_log_stats 设为 false，或显式打开 vLLM metrics/Prometheus；
2. 对每个请求记录 prompt token 数、cached token 数、cache hit token 数和请求所属 replica；
3. 记录 cache reset、sleep/wake 时间点；
4. 以同一批输入比较 prefix cache 开启/关闭时的 prefill latency、decode throughput、GPU KV 使用量和 wall-clock 时间；
5. 按训练 step、同一多轮 session 和同一 replica 分层汇总，避免跨 reset 聚合造成假命中率。

## 5. 并行计算与批处理

### 5.1 Agent loop 层：batch 内异步并发

AgentLoopWorkerBase.generate_sequences 为 batch 中的每个样本创建一个 asyncio.Task，最后用 asyncio.gather 等待全部结果。这个层面允许多个样本的环境交互和 LLM 请求重叠。

三组配置为 data.train_batch_size=2，因此每个训练 batch 至少有两个样本级 agent-loop task；折叠 agent 还可能从一个输入展开多个 trajectory。rollout.n=2 表示每个输入请求两次采样，不能简单等同为固定的最终 trajectory 数，因为环境的 session/retry/max-traj 逻辑还会影响实际保存数量。

### 5.2 vLLM 层：连续批处理与 token budget

vLLM async server 使用 AsyncLLM.from_vllm_config，生成通过 self.engine.generate(...) 返回异步 generator。引擎侧的两个关键限制是：

- max_num_seqs=8：同时调度的序列数上限
- max_num_batched_tokens=16384：一次调度的 token budget

因此真正的并发是“上层异步请求 + vLLM scheduler 连续批处理”的组合。长 prompt/observation 会快速消耗 token budget，样本数多不一定意味着所有请求同时执行。

### 5.3 Ray/server/TP 层：请求分发和模型并行

每个 rollout replica 按 rollout world size 创建；当前 rollout TP=2，pipeline parallel=1。vLLM 引擎实际日志确认 tensor_parallel_size=2。多 server 时，管理器用 least-requests 做分发，并用 sticky session 保持多轮会话的 server 归属。

agent.num_workers=1 只表示每个 agent-loop manager 创建一个 Ray agent-loop worker。它不是 vLLM 的 max_num_seqs，也不关闭 batch 内的 asyncio 并发；但它会限制 agent-loop worker 层的扩展度。

### 6.1 Frozen-reference 是额外开销，不是 cache 优化

Trace+FoldGRPO 和 Trace-only 的启动参数使用 trace_credit_source=frozen_reference，并指定单独的 Qwen3-8B reference model；no-Trace 的 run_summary 则是 TRACE_CREDIT_SOURCE=none。FrozenReferenceScorer 在 agents/trace_reference_online.py:49-107 中冻结梯度并进入 inference mode，但每个 context view 都重新运行一次完整 prefix 前向，且 use_cache=False。

这条路径节省了反向图，但没有复用前一个决策前缀的 KV cache，也没有把多个 context view 合成 batch。因此它会显著增加两组 Trace 的推理计算量，并占用额外 GPU 显存。三组 wall-clock 或 GPU-hours 对比必须单独列出该 reference scorer，不能只比较 rollout token 数。

## 7. 对三组 rollout 统计的解释影响

现有三组报告显示 Trace-only 的 response context 和 observation 更长，且 retained rollout 更多。这个现象不能直接解释为 cache 更有效或计算更省：

- prefix cache 是否命中没有记录；
- 每轮训练模式切换可能 reset prefix cache；
- 更长的 observation 会增加 prefill token 负担，即使部分前缀命中也不代表总 wall-clock 更低；
- Trace-only retained trajectory 更多，本身就是额外的 sample/compute budget confound；
- generated tokens、response tokens 和保存 transcript 长度不是同一指标，不能替代 vLLM cached-token 统计。

因此当前更稳妥的表述是：**三组共享同一套以 vLLM prefix caching、async scheduling、批量 token budget、TP 和 FSDP/sequence-parallel 为核心的计算框架；实验变量主要是 Trace/FoldGRPO 行为和 reward，不是 cache policy。现有产物足以证明优化开关和执行路径，但不足以证明三组之间存在不同的 cache 命中收益。**

## 8. 下一轮建议的最小埋点

建议新增每个 rollout 请求一行结构化记录：

step, sample_id, trajectory_id, replica_id, request_id, prompt_tokens, generated_tokens, cached_tokens, prefix_cache_hit, prefill_ms, decode_ms, kv_cache_usage, cache_reset_epoch

并固定以下对照：

- A：当前配置，prefix caching 开启；
- B：仅关闭 enable_prefix_caching；
- C：保持 cache 开启但打乱 server 归属，验证 sticky session 的贡献；
- D：固定 retained trajectory 数，消除 Trace-only 样本量差异。

比较指标至少包括：cache hit token ratio、prefill latency/token、decode tokens/s、每题 wall-clock、GPU-hours、每 1k context token 的成功率，以及 cache reset 前后的命中率和显存占用。

没有这些埋点时，建议把“启用了缓存”与“缓存带来收益”严格分开记录。
